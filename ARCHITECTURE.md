# Character Sheet App architecture

## Refined Sheet (fourth presentation)

See [REFINED_SHEET.md](REFINED_SHEET.md) for its implementation boundaries,
extension-point map, feature-parity checklist, and verification tools. It is
registered in `app/ui/sheet_types.py`, lives in `app/ui/refined/`, and reuses the
existing rules and workflows. Its per-character presentation records and undo
history are isolated from Customizable, Original Spheres, and Ultra.

The application is organized so saved data, rules, presentation, and Qt interaction can evolve independently. Existing SQLite tables and model fields remain the compatibility boundary for saved characters.

## Where new work belongs

- **Shared class-package extensions:** choice options may declare `minimum_level`; a provider may reuse another fixed-option catalog with `options_from_provider` instead of copying it. Keep the referenced provider independent (no chained references). Embedded archetypes that have no separate catalog page belong in `app/class_packages/definitions/archetype_sources/`; both the catalog loader and archetype generator consume these supplemental source records. Rising counters such as Vitae use resource declarations `use_increases` and `restore_toward_zero`; `recovery_progression` keeps recovery amounts in the shared rules layer. Crimson Dancer, Mountebank, and Reaper are examples of these extension points. Their situational trackers do not imply automatic adjudication of every published ability.

- **New page or page placement:** add the page composition in `app/ui/pages.py`. Build reusable page sections in `app/ui/sheet_sections.py`; do not assemble page layouts in `CharacterSheetWidget`.
- **Reusable controls:** add section shells, record tables, content-sized tables, action menus, details panels, or numeric fields in `app/ui/components.py`. Feature-specific saved-list layouts belong in `app/ui/feature_sections.py`. Built-in default column sets live in `app/ui/table_profiles.py`; keep these concise and put full saved rules in hover/details instead of duplicating internal state or choice columns.
- **User-adjustable table columns:** `app/ui/table_layout.py` owns persistent column widths, visual order, hidden built-in columns, and user-created presentation columns. Register tables through `SheetCustomizationController` using stable section/table identifiers; do not save column structure in page or rules code. In Build Mode, header dragging moves/resizes columns and the header context menu adds, renames, removes, or restores them. Built-in columns keep stable `builtin:N` identities; custom columns use UUID identities and presentation-only cell values, so ordinary record refreshes and rules calculations remain unaware of visual column choices. Merely entering Build Mode must not serialize responsive widths: only a real header interaction marks a table user-modified. Legacy width-only snapshots are intentionally discarded so previously captured transient geometry self-heals.
- **Proportional box scaling:** `app/ui/content_scaling.py` owns the optional Build Mode behavior that scales a registered block's fonts, fields, controls, spacing, and table rows with its geometry. Keep this presentation-only; section code and calculations must never inspect the saved scale. New `custom_sections` participate without page-specific scaling code.
- **Per-character sheet arrangements:** `SheetCustomizationController.capture_state()` and `apply_state()` are the only bridge between presentation settings and persistence. `CharacterRepository` stores that opaque snapshot in `character_sheet_layouts`, and character export/import carries it as optional `sheet_layout` data. Do not add box geometry, colors, column widths, or content scale fields to gameplay models.
- **Presentation undo/redo:** `app/presentation_history.py` captures bounded, per-character snapshots through that same arrangement bridge plus Building Blocks state. All completed presentation mutations—box/cell geometry, tabs, blocks, colors, content scale, and table structure—must enter this shared history once per user gesture. When only cell overrides differ, `CharacterPage._apply_presentation_snapshot()` must use the repository's cell-only transaction and update `NestedCellEditor` in place; rebuilding tabs and block widgets for a cell drag is both unnecessary and visibly slow. Never add gameplay/rules records to these snapshots; text editors retain their native local undo before Ctrl+Z/Ctrl+Y falls back to sheet history.
- **Character navigation and files:** the File menu in `app/ui/main_window.py` owns New, Switch Character, Save, and Save As. Character edits continue to persist immediately in SQLite; Save/Save As create portable `.character.json` files and remember the last file path per local character.
- **Feature category:** register it in `app/feature_registry.py`. Reuse the common presentation helpers in `app/presentation.py`, and add category-specific browser/editor dialogs in `app/ui/dialogs.py`.
- **Play books:** optional wide play interfaces are projections over existing character records, never replacement databases. Traditional spells and magic effects use `app/spellbook.py`; martial talents use `app/martial_book.py`. Their dialogs render/search current entries and call bounded service actions. New talent resource requirements should be exposed as structured automation metadata and resolved in the service; Qt must not deduct resources or interpret rules prose itself.
- **Inventory organization:** `app/inventory_organization.py` is the sole classifier and snapshot service for the wide Inventory organizer. Automatic category/subcategory placement comes from catalog metadata with stable fallbacks; `inventory_item_placements` stores only explicit per-character overrides and `inventory_custom_groups` stores user-created drop targets. Drag/drop, Ctrl+Z, and Reset operate on those presentation snapshots and must never rewrite equipment category, state, slot, quantity, enchantments, weight, or automation. Category lists persist an explicit placement; dropping onto organizer whitespace calls `reset_item()` and removes only that item's override so catalog classification resumes. Character export/import remaps placement item IDs alongside ordinary equipment IDs.
- **Hover text or selected details:** extend `app/presentation.py`. All rules-bearing rows should use `readable_tooltip`; saved rules features should use `feature_summary_text` and `feature_details_html`.
- **Reactive formulas:** `app/character_formulas.py` owns every stable character reference, alias, autocomplete description, and default-false/default-zero behavior. Rules-bearing sheet editors call `CharacterSheetWidget._refresh_formula_dependents()` after persistence; that one seam refreshes Movement, conditional-attack visibility, custom trackers, and emits `formula_values_changed` for runtime Building Blocks. Never make a formula consumer listen directly to individual ability, feat, resource, Sequence, or item widgets. `FormulaNumberEdit` shows a resolved number while idle and reveals its saved source only during editing, so pages and dialogs must not reproduce that behavior themselves.
- **Symbolic dice:** `FormulaEngine.evaluate_symbolic_dice()` is the sole damage-expression path that preserves `XdY` terms until an explicit attack roll. Attack services convert those terms into ordinary `ExtraDamageComponent` records, so every sheet type displays and rolls the same expression. Numeric fields still use `evaluate()`; do not average dice or build a second damage parser in a dialog.
- **Theme:** change the single base stylesheet or its palette substitutions in `app/ui/theme.py`. Widgets should expose semantic `objectName` roles instead of carrying their own theme colors.
- **Sheet types:** register every interchangeable whole-sheet presentation in `app/ui/sheet_types.py`; the Main Window creates and switches registered presentations without changing character data. Alternate presentations consume the read-only `CharacterSheetSnapshot` from `app/services/sheet_presentation.py`, so calculations, automation, persistence, and sheet geometry remain independent. Fixed reproductions keep their artwork under `app/assets/sheet_types/<key>/` and declare `supports_customization=False`; Building Blocks and per-character geometry continue to belong exclusively to the customizable sheet. A new type needs one widget with `load_character()` and `refresh_all()`, one registry entry, and focused geometry/switching tests—no Main Window branch or duplicated rule calculation.
- **Ultra Sheet modules:** `app/ui/ultra_modules.py` is the capability-driven extension point for the fixed, responsive Ultra Sheet. A future subsystem registers one `UltraModuleDescriptor` with a stable key, target page, factory, order, and capability requirements; `UltraSheetWidget` discovers and places it without page-specific branching. Add capability tokens through class/archetype catalog metadata and `ClassCapabilities.extra`, not by testing class names in Ultra panels.
- **Customizable-sheet presets:** named starting arrangements live in `app/ui/sheet_layout_presets.py`. Character type resolves the initial preset; `Default Spheres` deliberately stores only its preset marker and uses the responsive composition in `app/ui/pages.py` until Build Mode detaches the blocks into freeform coordinates. A preset serializes through the existing per-character customization state, so Build Mode may alter it freely and reset can reapply it without touching rules data. Coordinate-based presets remain supported for genuinely fixed presentations, but should not be used for the normal scalable desktop sheet.
- **Freeform box sizing:** when Build Mode detaches a section, `SheetCustomizationController` marks its tables as `fillAvailableHeight`. Shared content-sizing helpers must respect that property: headings, notes, and action rows keep their layout positions while the record table consumes added height. Never reapply a fixed table height from a refresh routine when its section is freeform-managed.
- **Calculation:** add pure PF1e/Spheres math in `app/rules.py` (or a focused rules module such as `app/spell_rules.py`). Coordinate persisted inputs through `app/services/character_calculations.py`; do not assemble modifier maps in widgets.
- **Character state:** add persisted dataclasses in `app/models.py`, migrations and CRUD in `app/database.py`, and calculation-facing fields in `app/services/character_state.py`. Never change or delete an existing saved-data field without an explicit migration and compatibility test.
- **File-dialog locations:** application-wide dialog history belongs in `QSettings` under `files/`; it is presentation preference, not character data. Character Save As uses the installed application folder until a successful save records `files/lastSaveDirectory`, then reuses that existing folder across characters. Per-character file paths remain in `files/characterPaths`.
- **Favored-class and movement providers:** `favored_class_bonuses` owns per-class HP, skill-point, and documented manual allocations; the calculation service emits only the HP allocation as a normal typed modifier. `movement_profiles` stores user bases/overrides for every movement mode, while `racial_land_speed()` and `CharacterCalculationService.movement_results()` resolve defaults and automatic effects. Pages and alternate sheet presentations consume those services; they never infer race speed or favored-class math themselves.
- **Sheet wheel input:** `forward_editor_wheel_to_page()` in `app/ui/components.py` is the single guard for spin boxes and closed combo boxes inside the customizable sheet. It forwards the gesture to the enclosing page scrollbar and consumes the editor event, so adding a new numeric/choice field never requires another wheel workaround. Combo-box popups remain independently scrollable.
- **Formulas, trackers, and numeric fields:** safe expression parsing lives exclusively in `app/formulas.py`; never pass user formulas to Python `eval`, SQL, or template execution. `CharacterFormulaContext` in `app/character_formulas.py` is the one character namespace for BAB, abilities, classes, skills/ranks, owned/enabled feats, martial focus, casting, resources, and custom trackers; its canonical `suggestions()` feed every editor's value/description autocomplete. `FormulaLineEdit` owns the shared keyboard/mouse suggestion popup and `FormulaNumberEdit` adds literal-or-formula validation plus a resolved preview. Formula-aware saved model fields attach expressions through `numeric_formulas` using stable entity/field identities and resolve in `CharacterCalculationService`; it evaluates them against a literal baseline snapshot to prevent an item or bonus from recursively redefining a value used by its own formula. The ordinary model value remains a backward-compatible fallback, and import remaps every record-owned formula ID. Persistent Calculated Value, Counter, and Resource Pool records remain in `custom_trackers`, with stable keys independent from labels and placement. Add a new formula reference once to `CharacterFormulaContext`, then document and test it—do not rebuild a field-specific namespace or autocomplete list in a dialog.
- **Recovery and rests:** `app/recovery.py` owns the Full Rest registry and execution. Built-in resources and custom trackers publish recovery targets there; UI code only chooses targets and displays the resulting report. Per-character overrides live in `character_rest_settings`. Add a new recoverable system by registering a stable target and handler in the recovery engine, never by adding an isolated reset button.
- **Runtime custom blocks:** `app/ui/tracker_blocks.py` renders one movable block per persistent tracker. Runtime blocks register through `SheetCustomizationController.sync_sections()` and use `tracker:<stable_key>` customization IDs, so placement is separate from rules state and remains portable across character exports.
- **Formula documentation:** the in-app reference is maintained in `app/formula_codex.py`. Whenever a new named value, operator, or function is exposed, update that Codex page and its search text in the same change.
- **Building Blocks:** `app/building_blocks/` is the single extension framework for current and future sheet boxes. `schemas.py` defines versioned definitions, instances, tabs, and cell overrides; `registry.py` registers built-in blocks and extensible cell types; `persistence.py` owns additive presentation-only tables; `runtime.py` renders custom definitions and adapts live built-in sections; `catalog.py` and `designer.py` provide the reusable catalogue and visual authoring UI; `nested_editor.py` extends Build Mode down to individual cells; and `tabs.py` projects per-character tab records into the sheet. A built-in section's saved `blockInstanceVisible` flag is combined with its independent `ruleAvailable` capability flag; a layout reload must never reveal a class system the character does not possess. Do not create a second page-builder or store gameplay data in these records.
- **Block registration:** expose a future live section in `CharacterSheetWidget.custom_sections` with a stable section key, then register one `BlockDefinition` in `register_builtin_blocks()`. Catalogue search, restore, per-character placement, tab movement, Build Mode, export, and import are automatic. A fully custom block needs only a global template definition and contains serializable `CellDefinition` records.
- **Cell types:** register a stable `CellTypeDescriptor` in `CELL_TYPE_REGISTRY`. The descriptor declares minimum geometry, supported behavior, optional configuration validation, and an optional runtime factory. The designer discovers descriptors dynamically. Cell factories receive only a Qt parent, the immutable cell definition, and a safe runtime context; they must never execute user code.
- **Bindings and actions:** add editable or read-only character values to `BINDINGS` in `app/building_blocks/bindings.py`. Bindings resolve through existing repositories/calculation services and never duplicate rules data. Add button behavior to the allowlisted `ACTIONS` registry in `actions.py`; user-entered Python, SQL, shell commands, and imports are never action types. Formula cells continue to use `app/formulas.py` exclusively.
- **Tabs and instances:** `sheet_tabs`, `sheet_block_instances`, and `sheet_cell_overrides` are character-specific presentation state. `building_block_templates` is the global reusable user catalogue. Tab names and visual labels are never keys. Removing/hiding a tab, block, or cell changes presentation only. The Building Blocks catalogue removes the selected visible instance from the selected page through `BuildingBlockRuntime.remove_block()`; it hides the placement while retaining its reusable template, cell configuration, gameplay bindings, and undo history. Built-ins remain registered and recoverable; user-template instances embed versioned definition snapshots so deleting or colliding catalogue entries cannot break placed characters.
- **Default Sheet restoration:** `BuildingBlockRepository.reset_character_presentation()` resets only per-character tabs, block instances, and cell overrides, then reseeds registered built-ins. `CharacterRepository.clear_character_sheet_layout()` clears the legacy presentation snapshot. The UI composes these operations through Build Mode’s Restore Default Sheet action; neither method may delete rules data or global user templates.
- **Nested geometry:** anchored custom and detached built-in cells scale proportionally with their parent; independent cells keep fixed pixel geometry. `NestedCellEditor.begin_parent_resize()` captures one geometry baseline per gesture, preview scales anchored cells from that baseline to avoid cumulative rounding drift, and the final parent save persists the resulting cell geometry once. Group IDs make selected children move as one unit. Existing complex Qt sections enter the system first as atomic built-in blocks, while `NestedCellEditor` creates stable adapter keys for safely detached controls. Before freeform editing, a built-in control must be removed from the exact nested Qt layout that owns it—even when its parent is already the block—or the layout will overwrite its geometry. A non-painting placeholder retains that layout slot only while a visible control is freeform, preventing neighboring content from collapsing or jumping mid-edit; removing the control removes the placeholder so the native layout immediately compacts. “Anchor to parent” deletes the freeform override and restores the widget to its recorded Qt layout slot, returning sizing, reflow, and input ownership to the original implementation. The editor also restores that slot when an override disappears, a history snapshot is applied, or Default Sheet is restored. Persist only at the end of a drag/resize operation, never on every mouse move.
- **Building Blocks migrations:** keep schema changes additive in `BuildingBlockRepository._create_schema()` and increment the exported presentation schema when serialized meaning changes. Character exports carry the complete per-character presentation plus embedded snapshots; older exports without this optional payload are seeded with the four default tabs. The feature repository shares the desktop process's SQLite transaction boundary while remaining a separate module, preventing competing Windows writers.
- **Building Blocks themes:** semantic object names (`runtimeBuildingBlock`, `runtimeBlockTitle`, `blockDesignerCanvas`) are styled centrally in `app/ui/theme.py`. Cell-level foreground/background/border/typography are optional user overrides layered above Classic, Light, and Dark; never fork component styles per theme.
- **Automation effect:** define catalog automation in `app/feat_automation.py`, `app/trait_automation.py`, or `app/talent_automation.py`. Apply shared effect semantics in `app/rules.py` so feats, traits, martial talents, and magic talents behave consistently. Global targets belong in `GLOBAL_TARGETS`; scoped families use a registered `DYNAMIC_EFFECT_TARGET_PREFIXES` prefix such as `sphere_save_dc:<sphere>`. `CharacterCalculationService` converts the shared `spell_points` target into `SpellPointContribution` records, so feats, traditions, and future class providers never rewrite the base pool formula.
- **Multi-stat sphere providers:** when one sphere rule changes several related systems or grants derived choices/ranks, register it as a catalog `provider` instead of scattering talent-name checks through widgets. `app/athletics_rules.py` is the reference implementation: it resolves packages, granted rank floors, physical-ability skill additions, armor-check mitigation, and movement projections; `CharacterCalculationService` applies those results to every sheet type and formula reference. Qt only gathers explicit package choices and renders the resolved state.
- **Bundled rules data:** access it through `app/catalogs.py`. `app/content.py` is the compatibility facade for older imports. Scrapers in `tools/` may update JSON under `data/pf1e`, but UI code should not read JSON directly.
- **Rules-catalog releases:** `app/catalog_versions.py` owns the manifest, integrity checks, staged installation, active-release selection, rollback history, export, and bundled fallback. A release is a ZIP whose root contains `catalog_manifest.json` plus the declared JSON files; installation must validate every declared path, size, SHA-256 hash, and JSON payload before replacing the active catalog. `RulesCatalog` continues to read only through `app/catalogs.py`, so UI and rules modules never need an update-specific branch. Character databases and user-created content are outside the release root and must never be copied, replaced, or removed by catalog updates.
- **Casting and martial traditions:** `tools/import_tradition_catalog.py` normalizes the official tradition pages into `data/pf1e/traditions.json`; runtime access is exclusively through `RulesCatalog.tradition_entries()` / `tradition_entry()`. `character_traditions` stores the selected catalog key, generic choice map, only the grant keys created by that selection, and an optional immutable custom-definition snapshot. `app/tradition_rules.py` is the shared resolver for catalog/custom definitions, drawback and boon currency, unused-drawback spell-point progressions, and deterministic `CastingTraditionAutomation` projections. Permanent drawback consequences emit declarative stat adjustments there and enter every sheet through `CharacterCalculationService.automatic_modifier_map()`; triggered or opponent-dependent clauses remain explicit reminders until a matching event/context provider exists. Do not parse rules prose in Qt or mutate saved statistics to apply a drawback. `TraditionCatalogDialog`, `TraditionChoiceDialog`, and `CustomTraditionDialog` render fixed grants, declarative choice groups, repeated drawbacks/boons, and custom sphere/talent packages. Applying a package delegates to the existing talent/sphere acquisition functions, and removal uses recorded grant ownership so it cannot erase a pre-owned feature. New catalog traditions should normally be data-only; custom traditions remain character-owned data, never widget-specific rule branches.
- **Magic sphere acquisition:** persist one stable `Base Sphere` ownership record. `app/sphere_rules.py` projects that ownership into the concrete, read-only base abilities shown on Page 3, including starting package choices and drawback filtering. Update the reviewed registry there; never persist duplicate ability rows just to render them.
- **Martial sphere acquisition:** `app/sphere_rules.py` owns initial package choices, inferred choices from tradition grants, free starting-talent translation, and the read-only abilities projected from a `Base Sphere` record. `app/drawback_rules.py` owns package/drawback access checks for both the catalog browser and final save operation. Store the selected package on the base record; persist a separate talent only when the sphere actually grants one (currently Equipment, Tech, and Alchemy Formulae), and synchronize that grant when the starting choice changes.
- **Sphere drawback restrictions:** package access and talent-selection restrictions live in `app/drawback_rules.py`. Catalog dialogs may explain and disable illegal choices, but the final add operation must call the same rules function so presentation changes cannot bypass enforcement.
- **Advancement budgets and ASIs:** `app/advancement_rules.py` is the pure provider for automatic skill-point, feat, sphere-talent, spell-repertoire, and level-based ability-increase allowances. `ability_score_increases` stores allocations separately from creation-time base scores; the calculation service adds them as a named source. `advancement_adjustments` stores only the character-specific manual delta, optional total override, and note; exports preserve both layers. The Page 0 tables are projections and must never embed class or sphere rules. New class progressions should enter through catalog metadata/table parsing or a focused provider extension, while unusual campaigns use the saved delta/override instead of changing global rules.
- **Equipment and items:** normalized Pathfinder and Spheres records live together in `data/pf1e/items.json`, distinguished by `source_group`, then `family`, `category`, and `subcategory`. Expose them only through `RulesCatalog`. Item automation is attached to those stable records by `app/item_effects.py`; do not create a second catalog or interpret descriptions during gameplay. Saved custom items remain valid because catalog identity and automation metadata are optional.
- **Item usage controls:** `effective_item_state()` and `preferred_item_state()` in `app/item_effects.py` are the shared state vocabulary for worn, wielded, armor, shield, carried, and stored items. Direct Wear/Remove controls must call the repository's state transition and silently no-op for no selection, zero quantity, or an already-matching state; never duplicate category-to-state rules or show an error dialog for an unavailable quick action.
- **Worn slots and encumbrance:** `worn_slot_catalogs` stores only an optional per-character ordered override; the canonical slot list remains a model default, so empty slots are always visible and old characters require no destructive migration. Repository state transitions enforce one active item per named slot. `carrying_capacity()` and `calculate_encumbrance()` in `app/rules.py` own PF1e size/Strength thresholds, load penalties, lifting, and speed; `CharacterCalculationService` combines those restrictions with armor by taking the worse limit rather than stacking duplicate penalties. Inventory widgets only project these results.
- **Class catalogs:** first-party playable classes live in `data/pf1e/pathfinder_classes.json` and are regenerated by `tools/import_class_catalog.py`. Every selectable Spheres class, family, full rules page, feature progression, casting declaration, and class-specific archetype lives in `spheres_classes.json` / `spheres_class_archetypes.json`, regenerated by `tools/import_spheres_class_catalog.py`. `RulesCatalog.class_entries()` is the only merged gateway. The picker, Special Abilities table, capability resolver, and Codex all consume that gateway; never add a second hard-coded class combo box.
- **Class archetypes and stacking:** Pathfinder plus Pathfinder-class Spheres archetypes live in `data/pf1e/archetypes.json`, regenerated by `tools/import_archetype_catalog.py`; Spheres-class archetypes use the class-page importer above. Both use the disposable `.archetype-source` cache. `class_level_archetypes` persists only stable selected keys. `app/archetype_rules.py` owns normal replaced-feature overlap, explicit compatibility/incompatibility, and requirements. It also normalizes Spheres prose such as “this archetype requires X or Y” into the same metadata shape; required base archetypes are intentional stacking exceptions. Any future class editor or import path must call that shared validator instead of implementing its own checkbox rules.
- **Archetype class features:** `app/class_feature_rules.py` is the single display resolver for base and archetype-granted class features. It removes fully replaced base features, preserves overarching features when only specific level instances are traded away, extracts named/leveled abilities from imported archetype prose, and supplies both the customizable Special Abilities block and alternate sheet presentations. Never filter feature names directly in a widget.
- **Optional archetype exchanges:** `archetype_optional_features()` discovers opt-in exchanges such as Greater Training from normalized archetype rules. `ClassLevelDialog` renders those options generically, checks their replacement conflicts, and stores selected stable keys in `class_feature_selections` with type `Archetype exchange`. Both advancement and class-feature resolution consume that same selection. New archetypes using the published exchange pattern therefore need data, not a class-specific checkbox or budget branch.
- **Archetype modifications and required choices:** `app/class_modifications.py` layers declarative statistics, casting, advancement, capability, and proficiency changes over the base class without changing saved base records or widgets. Imported archetypes declare these changes under `class_modifications`. `app/archetype_rules.py` validates any number of `choices` groups with stable keys, level, minimum/maximum picks, and option-specific modifications. `app/archetype_presentation.py` is the shared, presentation-only projection that turns imported prose into a replacement overview and feature-by-feature rules blocks for both the picker and Codex; do not independently format archetype prose in a dialog. Spheres imports commonly use meaningful single newlines instead of blank paragraphs, so the shared formatter recognizes their feature headings, labeled sub-options, and replacement clauses while leaving the catalog's exact rules text unchanged. `ClassLevelDialog` renders one-choice and multi-choice groups automatically; values remain backward-compatible `class_feature_selections` records of type `Archetype choice`. Calculations, advancement budgets, casting, and `resolve_class_features()` consume the same declarations. Add future archetype decisions to catalog data—never create a class- or archetype-named checkbox branch.
- **Archetype selection UI:** both new-class and existing-class workflows use `ArchetypeSelectionDialog`. Its first column contains real `QCheckBox` controls rather than relying on editable table-item check states, because the rules table itself is intentionally read-only. `ArchetypeCompatibilityIndex` precomputes catalog compatibility metadata for responsive candidate checks: after every selection, incompatible unselected choices are disabled and rendered with the theme's disabled-text color, while selected choices remain enabled so they can always be removed. The Add Class dialog retains selected stable keys until the new class row exists, then persists them through `set_class_archetype_keys()`; do not defer first-level archetypes to a later edit operation.
- **Class capabilities and sheet tiers:** `app/class_capabilities.py` resolves `traditional_spells`, `magic`, `martial`, `skill`, and `sequence` per class row before combining multiclass results. `app/ui/pages.py` always composes the universal foundation and conditionally reveals the traditional-spellcasting or Spheres tiers from those resolved values. Add a future class system as a declarative capability and registered section; do not test class names in page layouts.
- **Shared casting progression:** `automatic_traditional_casting()` keeps unrelated Pathfinder caster levels separate and honors delayed caster-level offsets; `automatic_sphere_casting()` stacks Spheres caster levels using catalog High/Mid/Low declarations. The Core-page Special Abilities table reads every selected class's level features from the same class catalog. Do not add another class-specific feature table or caster-level calculation in UI code.
- **Traditional spell picker:** `TraditionalSpellCatalogDialog` and `CatalogSearchIndex` remain the shared traditional-spell browsing boundary. The result table deliberately prioritizes sortable spell name, effective level, school, and ruleset; publisher, complete class lists, and rules text belong in the details panel. Preserve the guaranteed name width and two-row filter layout when adding future spell filters.
- **Traditional spell records:** Page 3 keeps traditional repertoire in the independently placeable `spells_known` block and Spheres effects in `magic_talents`. `CharacterSheetWidget._refresh_spells_known()` projects non-Sphere saved `Spell` records into Spell, Spell Level, School, Casting Time, and Range; the Spheres table continues to project spell-point cost through `spell_record_presentation()`. A future prepared-spell or spells-per-day block should consume the same saved records and casting metadata rather than recombining these systems.
- **Selected spell summary:** known, prepared, and Spheres spell tables report selection through `CharacterSheetWidget._select_spell_for_summary()`. The shared casting summary derives the visible save DC from that selected record and the calculation service's casting/DC modifiers. Keep selection wiring in the table projection and calculation semantics in the service/rules layer; alternate spell tables should reuse this seam rather than adding another DC field.
- **Prepared spell subsystem:** `prepared_spells` stores per-class preparation rows separately from known spells, with an optional `known_spell_id`, explicit Custom catalog snapshot, prepared count, and expended count. `app/prepared_spell_rules.py` owns 9-level, 6-level/extract, delayed 4-level, and casting-ability bonus capacity calculations. `spells_prepared` presents both per-level capacity and individual remaining copies. Normal preparation must reference `spells`; Custom is the sole exception. `FullRestEngine` owns restoration through the configurable `prepared_spells` target. Export/import remaps both class-row and known-spell foreign keys.
- **Spontaneous spell subsystem:** `app/spontaneous_spell_rules.py` owns the High, Mid, and Low daily-slot progressions and casting-ability bonus calculation. `spontaneous_spell_slots` persists expenditure by character, class row, and spell level—never by individual known spell. The shared spell overview consumes both prepared and spontaneous capacity providers, while spontaneous usage has its own level-based controls. `FullRestEngine` restores it through the configurable `spontaneous_spell_slots` target, and export/import remaps its class-row foreign key. Future class or archetype overrides belong in the rules provider or declarative casting profile, not in page widgets.
- **Traditional caster projection:** `app/traditional_spellcasting.py` resolves effective class/archetype casting declarations and produces prepared or spontaneous capacities without importing Qt. The existing page tables, Spell Book, and future sheet presentations must consume these providers instead of independently resolving class casting or slot progressions.
- **Spell Book:** `app/spellbook.py` projects the character's existing `spells`, `prepared_spells`, spontaneous slot usage, generated base-sphere abilities, and spell-point pool into immutable book entries. It is the only mutation boundary for Cast, Use, Restore, and direct remaining-value correction in the optional book; it never duplicates catalog data or preparation maxima. Traditional entries are gated by the effective archetype-aware casting state in `app/traditional_spellcasting.py`: when selected archetypes remove every class-backed traditional casting feature, dormant saved spell and preparation rows remain preserved but are neither displayed nor actionable. A retained caster in a multiclass build keeps the traditional book available. `app/ui/spellbook_dialog.py` is a modeless, searchable renderer with a 400 ms shared debounce and reusable rich tooltips. New spell providers should extend the importer and normalized record shape, not the dialog or database schema.

Spell collection and search links open complete local Codex entries without creating thousands of tree nodes. Casting packages, general drawbacks, sphere-specific drawbacks, dual-sphere drawbacks, boons, and martial sphere drawbacks all enter through `RulesCatalog.tradition_rule_entries()` and the same search projection; do not create Codex-only copies. New Codex-bearing features should extend those projections rather than adding a parallel search implementation.

Add future visibility-controlled records through the same formula/presentation boundary, not arbitrary code or widget-local state.

Pathfinder and Spheres are peer class branches; class-specific shortcuts must not be hard-coded into the menu hierarchy. A specialized class renderer may remain behind its normal catalog class node when it documents additional interactive systems.

Keep it representative rather than class-specific production code; run it against a temporary database before deployment and the live database only after making a user-data backup.

New large catalog browsers should select searchable fields through `CatalogSearchIndex`, default to name search, debounce free-text input, and cap rendered rows independently from the total match count. Do not rebuild searchable description strings or thousands of table cells on each keystroke.

Future repeatable skills must extend this projection rather than creating a second skill calculator or table.

Future annotations should extend the note manager instead of adding page-specific overlays.

Martial and magic catalog dialogs share this key; new talent catalogs should reuse it instead of hard-coding category lists in Qt.

## Runtime flow

1. `CharacterRepository` loads and saves stable model records.
2. `CharacterStateSnapshot` assembles immutable calculation input.
3. `CharacterCalculationService` combines that state with pure functions from `app/rules.py`.
4. `CharacterSheetSnapshot` projects those results for any registered whole-sheet presentation.
5. The selected sheet-type widget coordinates its own interaction and refreshes.
6. Section, page, component, presentation, and theme modules render the result.

## Racial traits and racial choices

- `data/pf1e/races.json` is the single catalog for race baselines, subraces,
  base racial traits, alternate racial traits, replacement declarations,
  structured choices, and reviewed automation. Runtime code must never infer a
  mechanical effect from a description.
- `CharacterDetails.race_trait_choices` stores generic `RaceTraitChoice`
  records: a stable trait key, a catalog-defined choice key, and one or more
  selected values. One trait can therefore own several independent choices
  without new columns—for example energy and shape, or terrain and spells.
- `app/race_rules.py` owns replacement resolution, conflict detection, choice
  validation, and conversion of safe catalog effects into `StatModifier`
  records, class-skill grants, senses, resistances, identity tags, situational
  reminders, advancement grants, and derived natural attacks. An invalid or
  incomplete required choice produces no partial automatic benefit.
- `RaceCatalogDialog` renders catalog `choice_specs`; it does not contain the
  rules for Dual Talent or any other named racial trait. Add a future choice
  widget kind through the shared choice renderer, then declare the options and
  constraints in the catalog importer.
- Replacement-sensitive systems such as Human Skilled and Bonus Feat must
  consume `resolved_racial_traits()` rather than checking the race name. This
  ensures alternate traits remove both their visible source trait and its
  advancement effect.
- Deterministic effects apply through the calculation service. Situational
  modifiers remain structured under `conditional_modifiers` and are never
  added to baseline totals merely because their trait is owned. Future combat,
  terrain, and target-state controls should consume that field instead of
  reparsing prose.
- Natural attacks are derived `Attack` records with stable negative IDs. They
  are not inserted into the character database, so selecting, replacing, or
  removing a racial trait immediately adds or removes the correct live rows
  without leaving stale attacks behind.
- Formula references are projected from the resolved race as `race.*`,
  `race_trait.*`, `sense.*`, and `resistance.*`. New presentations consume the
  same resolved providers instead of maintaining separate race logic.
- Choice types should be added in reusable families: fixed distinct options,
  skills, abilities, weapons, languages, energy/terrain, spells, catalog
  entries, and free text. Each reviewed trait declares effects separately from
  its choices so a choice can be recorded before every situational rule is
  automated.
- Run `tools/audit_racial_trait_automation.py` after catalog/importer changes.
  Choice candidates are a review queue, not permission to parse descriptions
  during character calculation.

## Safe extension checklist

1. Preserve existing model defaults and database migrations.
2. Add focused rule/service tests before wiring a new control.
3. Register new feature categories and reuse shared presentation components.
4. Run the focused affected tests, then the complete suite.
5. Render every affected page in Classic, Light, and Dark themes before deployment.

## Item automation extension points

Stages 1–3 use one path for belts, headbands, wondrous items, weapons, armor, and shields:

1. `RulesCatalog.item_entries()` returns the existing stable catalog record plus its reviewed `item_automation` projection.
2. `EquipmentItem` persists the optional catalog key, immutable automation snapshot, generic choices, explicit state, enhancement fields, and weapon profile. Old records receive migration-safe defaults.
3. `app/item_effects.py` validates choices, checks activation state, and converts applicable effects into the same typed `StatModifier` inputs used by feats, traits, talents, and custom modifiers.
4. `CharacterCalculationService` is the sole coordinator that adds item modifiers to character calculations and linked-weapon bonuses to one attack.
5. Page-specific UI only changes state, choices, component values, or the attack link; it never encodes an item rule.

Live market value follows the same boundary. `EquipmentItem.value_gp` is the
stable mundane/catalog base value; `app/item_enchantments.py` derives the
masterwork surcharge, total modified-bonus price, registered flat-price
properties, and final market value. Inventory, Original Spheres, Ultra, and
editor presentations consume that projection rather than maintaining their
own price formulas.

Use these seams for future additions:

- **New target:** add the stable target label to the shared model/presentation registry, then consume that target in the appropriate pure calculation. No item-family or page code should change.
- **New operation:** extend `ItemEffectSpec.operation` resolution in `app/item_effects.py`. Keep `add`, `set`, equipment `component`, weapon `grant_dice`, and critical/profile changes distinct rather than disguising them as global bonuses.

## Bonded companion extension points

`app/animal_companion_rules.py` owns the druid-style Animal Companion page,
including Beastmastery stacking. `app/bonded_companion_rules.py` owns the
registry for familiar-like pages and resolves class features, selections, and
the Beastmastery Pet talent into a `BondedCompanionGrant`. The shared
`BondedCompanionPanel` renders those grants. Add a future pet/familiar provider
to that registry and progression resolver; do not create a class-specific tab
or copy familiar calculations into a page widget. Character-owned names,
species, current HP, choices, and notes stay in `bonded_companions`, while
effective levels and progression benefits remain derived.

Published normal-familiar forms live in `data/pf1e/familiars.json`, regenerated
by `tools/import_familiar_catalog.py`. A saved Pet/Familiar record stores only
the stable `familiar_key` and character-specific overrides. The pure
`calculate_familiar_statistics()` projection combines that immutable creature
baseline with live master HP, BAB, base saves, effective Hit Dice, and familiar
progression. `FamiliarCatalogDialog` is only a searchable presentation over the
same catalog. Add future familiar forms to the importer/catalog, not to the Qt
page or database schema. Derived maximum-HP changes must pass through
`reconcile_familiar_hit_points()` so level changes preserve existing damage.
- **New activation requirement:** extend `ITEM_STATES`/`effect_is_active` and the generic state selector together. Activated abilities, durations, charges, and consumables intentionally remain future state providers, not booleans added to individual items.
- **New choice type:** extend `ItemChoiceSpec` and `validate_item_choices`; the generic `ItemChoiceDialog` renders every registered group. Validation must also remain in the repository so imports and non-UI callers cannot save invalid choices.
- **New family pattern:** add one narrowly reviewed branch to `automation_for_entry`. Match stable family data or an exact reviewed name, emit explicit effects, and add an independent provider test. Do not parse prose at runtime.
- **Per-item exception:** add an exact reviewed override before the generic equipment/weapon fallback and record unsupported portions in `rules_only`. Never mark an entry `full` unless all rules-bearing portions are represented safely.
- **Weapon property:** store safe static profile values on the equipment record and resolve them only for an attack whose `equipment_id` points at that wielded weapon. Conditional properties such as target-dependent damage remain structured rules-only metadata until an encounter context exists.
- **Dynamic attack profile:** register reusable attack templates and contextual profile resolution in `app/attack_profiles.py`. A saved attack keeps its stable `profile_key`, editable fallback values, and `damage_ability_mode`; automatic mode may react to current talents, feats, class progressions, equipment, and properties, while manual mode always preserves the player's selected damage ability. `AttackDialog` treats “None” as a ×0 ability contribution and restores ×1 when a manual ability is selected, after which the multiplier remains explicitly user-editable. Page code renders the resolved copy and never overwrites the saved fallback.
- **Composable item properties:** the complete normalized PF1 weapon/armor/shield property catalog lives in `data/pf1e/enchantments.json`, regenerated by `tools/import_enchantment_catalog.py`; caster level, aura, construction requirements, restrictions, bonus equivalents, and flat-price additions remain distinct fields. `app/item_enchantments.py` loads that catalog and owns host compatibility, modified-bonus validation, mutually exclusive upgrades, and the reviewed typed-effect overlay. `app/attack_profiles.py` resolves base weapon data before property operations such as critical-range expansion, damage-size scaling, ability substitution, and typed additional dice; `AttackResult` carries extra dice separately so critical multiplication and rolling remain correct. `equipment_enchantments` stores only stable property instances attached to an item, while the repository atomically supplies the required +1/masterwork host on the first property. The Codex and item-aware chooser consume the same records. Add a new deterministic effect to the keyed overlay and shared resolver operation; keep target-dependent effects as visible conditional rules until a target/activation context can resolve them safely. Do not fork the catalog, parse prose at runtime, or add bespoke UI checkboxes per property.
- **Spheres unarmed progression:** keep sphere-count rules, drawback exclusions, virtual talents, native Monk/Brawler interaction, and size scaling in `app/attack_profiles.py`. Add future rules that change which spheres count through a service-provided extension set or another reviewed virtual-count provider; do not mutate the talent catalog or persist calculated dice.
- **Armor or shield property:** update the item component (base bonus plus enhancement) and require the `armor` or `shield` state. Do not emit a second globally stacking armor/shield enhancement modifier.
- **Future conditional or activated effect:** add a separate context/state provider and teach the shared resolver to return an explicit active/inactive reason. Do not add item-specific checkboxes to a page.

Run `python -m tools.audit_item_automation` after provider or catalog changes. The generated `data/pf1e/item_automation_audit.json` reports every stable item key, automation status, choice requirement, ambiguous partial records, and missing weapon structure.

Resource and passive-effect abilities may use `higher:<ability>,<ability>`; passive effects can replace one ability contribution with another, impose a level-derived cap, and apply only when the replacement is better. Pools may spend another resource through `external_cost_key`, allowing Striker techniques and similar actions to share one authoritative tracker. Multi-choice resources with a separate capacity progression represent maintained inventions without creating one UI implementation per invention type. Weighted class systems may also declare `bonus_feat_replacement_choice_provider` and an exact point-to-level exchange schedule, as Conscript does. Archetypes that replace a normal talent progression declare `talent_replaces_base` and `talent_bonus_levels` in their reviewed advancement profile.
